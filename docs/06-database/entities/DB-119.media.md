# DB-119 — Media

## 1. Objetivo

`Media` representa o registro persistido de uma mídia utilizada pelo Bairu.

A entidade armazena os metadados necessários para localizar e gerenciar o arquivo físico mantido em um provedor externo de armazenamento.

O conteúdo binário da mídia não é armazenado no PostgreSQL.

---

## 2. Responsabilidade

`Media` é responsável por:

- identificar uma mídia;
- identificar o provedor de armazenamento;
- armazenar a referência técnica do arquivo;
- armazenar características básicas do arquivo;
- permitir o gerenciamento do lifecycle da mídia.

`Media` não é responsável por:

- regras de negócio da entidade consumidora;
- upload diretamente pelo domínio;
- armazenamento do conteúdo binário;
- definição de cardinalidade da mídia em cada entidade.

Essas responsabilidades pertencem ao Media Module e aos módulos consumidores.

---

## 3. Estrutura

Campos previstos para o MVP:

| Campo               | Tipo        | Obrigatório | Descrição                                     |
| ------------------- | ----------- | ----------: | --------------------------------------------- |
| `id`                | UUID        |         Sim | Identificador da mídia                        |
| `provider`          | VARCHAR     |         Sim | Provedor de armazenamento utilizado           |
| `provider_asset_id` | VARCHAR     |         Sim | Identificador do recurso no provedor          |
| `storage_key`       | VARCHAR     |         Sim | Referência utilizada para localizar o recurso |
| `mime_type`         | VARCHAR     |         Sim | Tipo MIME do arquivo                          |
| `file_size`         | BIGINT      |         Sim | Tamanho do arquivo em bytes                   |
| `created_at`        | TIMESTAMPTZ |         Sim | Momento da criação do registro                |

Os campos definitivos devem permanecer alinhados à implementação do Media Module e ao `CON-007`.

---

## 4. Relacionamento com o Domínio

No MVP, uma `Media` pertence a uma única entidade consumidora.

A relação é realizada pela entidade de domínio através de uma referência para `Media`.

Exemplo:

```text
Company
├── profile_media_id → Media
└── cover_media_id   → Media
```

ou:

```text
CompanyCatalogItem
└── media_id → Media
```

A cardinalidade e o papel da mídia são definidos pela entidade consumidora.

---

## 5. Compartilhamento

Uma mesma `Media` não deve ser compartilhada entre diferentes entidades de domínio no MVP.

Exemplo não permitido:

```text
Company A ──┐
            ├── Media X
Company B ──┘
```

A relação esperada é:

```text
Company A ── Media A
Company B ── Media B
```

Essa decisão simplifica ownership, substituição, exclusão e lifecycle.

---

## 6. Provider

`provider` identifica o provedor responsável pelo armazenamento físico.

No MVP:

```text
provider = Cloudinary
```

O campo existe para evitar que o modelo de dados fique implicitamente acoplado a um único provedor.

A entidade `Media` não deve armazenar credenciais ou configurações do provedor.

---

## 7. Provider Asset ID

`provider_asset_id` representa o identificador do recurso fornecido pelo storage provider.

Esse identificador é utilizado pelo Media Module para operações como:

- localizar o recurso;
- substituir a mídia;
- remover o arquivo.

O identificador não deve ser exposto como parte do contrato das entidades de domínio.

---

## 8. Storage Key

`storage_key` representa a referência técnica utilizada pelo sistema para localizar o recurso no storage.

Sua estrutura depende do provedor e da implementação do adapter.

As entidades de domínio não devem interpretar ou manipular esse valor.

---

## 9. Características do Arquivo

`mime_type` identifica o tipo MIME validado do arquivo.

No MVP, são suportados:

```text
image/jpeg
image/png
image/webp
```

`file_size` registra o tamanho do arquivo em bytes.

A validação dos tipos e limites de tamanho ocorre no Media Module, conforme definido no `CON-007`.

---

## 10. Integridade

Uma `Media` só deve ser persistida quando existir uma referência válida ao arquivo no storage.

O fluxo esperado é:

```text
Arquivo
   ↓
Validação
   ↓
Storage Upload
   ↓
Media
   ↓
Associação ao domínio
```

O registro não deve ser criado antecipadamente apenas para reservar uma referência.

---

## 11. Exclusão

`Media` utiliza Hard Delete no MVP.

Quando a mídia deixar de possuir uma associação válida no domínio:

1. o arquivo físico deve ser removido do storage;
2. o registro `Media` deve ser removido do banco.

A ordem operacional deve seguir o fluxo definido no `CON-007`, considerando possíveis falhas entre PostgreSQL e storage.

---

## 12. Lifecycle

O lifecycle técnico da `Media` é:

```text
Created
   ↓
In Use
   ↓
Replaced / Removed
   ↓
Hard Deleted
```

Não será utilizado um campo `status` para representar essas etapas no MVP.

O estado da mídia pode ser determinado pelo seu uso no domínio e pelo lifecycle operacional.

---

## 13. Índices

O campo `id` possui o índice da Primary Key.

Devem ser considerados índices ou constraints de unicidade para referências técnicas do provedor quando necessário.

Exemplo:

```text
(provider, provider_asset_id)
```

A decisão definitiva deve considerar se o provedor garante unicidade global do identificador e como o adapter de storage será implementado.

Índices adicionais somente devem ser introduzidos conforme as consultas reais do Media Module.

---

## 14. Constraints

Devem ser aplicadas:

- `PRIMARY KEY` em `id`;
- `NOT NULL` em `provider`;
- `NOT NULL` em `provider_asset_id`;
- `NOT NULL` em `storage_key`;
- `NOT NULL` em `mime_type`;
- `NOT NULL` em `file_size`;
- `NOT NULL` em `created_at`;
- `file_size >= 0`.

Os formatos de imagem permitidos devem ser validados pelo Media Module.

---

## 15. Dados Derivados

`Media` não possui dados derivados relevantes no MVP.

Os metadados armazenados representam informações persistidas sobre o recurso no momento de sua criação.

URLs públicas ou URLs de CDN não devem ser tratadas como fonte de verdade persistida nas entidades de domínio.

Quando necessário, devem ser obtidas pelo Media Module ou pelo adapter do provedor.

---

## 16. Auditoria

Operações relevantes sobre `Media`, especialmente exclusões administrativas ou operações sujeitas à política de auditoria, poderão gerar registros em `AuditLog`.

Exemplo:

```text
Media
  ↓
HARD_DELETE

AuditLog
  ↓
MEDIA_DELETED
```

O `AuditLog` não deve armazenar:

- conteúdo binário;
- cópia do arquivo;
- dados desnecessários da mídia.

As regras gerais de auditoria estão definidas no `CON-008`.

---

## 17. Decisões Importantes

| Decisão                             | Justificativa                                     |
| ----------------------------------- | ------------------------------------------------- |
| Conteúdo binário fora do PostgreSQL | Evita armazenar arquivos diretamente no banco     |
| `Media` armazena somente metadados  | Mantém separação entre domínio e infraestrutura   |
| Storage externo                     | Permite uso de CDN e serviços especializados      |
| Cloudinary no MVP                   | Atende às necessidades atuais de imagens          |
| `provider` persistido               | Evita acoplamento estrutural a um único provedor  |
| Uma `Media` por consumidor no MVP   | Simplifica ownership e lifecycle                  |
| Sem compartilhamento                | Facilita substituição e exclusão                  |
| Hard Delete                         | Evita manter registros técnicos sem finalidade    |
| Sem `status`                        | O lifecycle pode ser determinado operacionalmente |
| Auditoria separada                  | Mantém `Media` livre de histórico de operações    |

Mudanças arquiteturais relevantes devem ser registradas como ADR quando apropriado.
